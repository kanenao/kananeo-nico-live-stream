# バージョン運用ルール

## バージョン形式

開発中は `X.Y.Z-alpha.N` を使用します。製品版の完成条件を満たすまではα版を継続します。

## ベース番号の変更基準

| 変更内容 | ベース番号 |
| --- | --- |
| 小規模な修正・改善 | `0.1.1` |
| 大きな機能追加・仕様変更 | `0.2.0` |
| 製品版として安定し、完成条件を満たした段階 | `1.0.0` |

変更の規模と成熟度を確認して判断し、機能追加のたびに機械的に番号を上げない。

### 自動判定の基準（α78以降）

- **バグ修正・小規模改善**：`X.Y.Z`の**Zを1増加**（例：`0.2.0-alpha.77` → `0.2.1-alpha.78`）。
- **新しい主要機能・大きな仕様変更**：開発中は`X.Y.Z`の**Yを1増加、Zを0**（例：`0.2.1-alpha.78` → `0.3.0-alpha.79`）。
- **README/テストのみ・変更なし**：アプリの新しい公開版を発行せず、不要なα連番の消費を避ける。
- **製品版1.0.0**：実機統合試験、重大不具合修正、Windows実機更新確認などの完成条件を満たしたときのみ別途判断し、コミット分類では自動昇格しない。
- `npm run version:bump`（`version:bump:auto`と同じ）は最新の公開タグ`vX.Y.Z-alpha.N`からの開発コミットと実際の変更ファイルを確認し、`feat:`（主要機能）ならマイナー、`fix:`や`feat(small):`などはパッチ更新にする。ツール・ビルドスクリプトのみの改善はパッチ扱いにする。曖昧な変更は安全側にパッチとして扱う。
- Gitのタグが未取得または新しいコード変更がない場合は中止する。開発コードをコミットした後に実行し、必ずテストを確認する。必要時は`version:bump:patch`/`version:bump:feature`で明示的に分類できる。
- バージョン番号を進める際は`alpha.N`も**必ず+1**。過去のREADMEやCHANGELOGの履歴は編集しない。

## α版の連番ルール

- `alpha.N` は更新ごとに1ずつ増やす。
- ベース番号が変わっても連番をリセットしない。
- 例：`0.1.1-alpha.94` → `0.2.0-alpha.95`
- バージョン表記は常に `X.Y.Z-alpha.N` とする。
- 製品版の完成条件を満たすまではα版を継続する。

## 製品版への移行条件

少なくとも、主要機能の実機統合試験、重大不具合の解消、データ移行・復旧の確認、セキュリティ確認、Windows配布物の検証、READMEと変更履歴の整備を完了し、安定運用できると判断できた段階で `1.0.0` へ移行する。CI成功だけを製品版完成の根拠にしない。

## 現在

現在のバージョン：`0.3.1-alpha.90`

`0.2.0` は、コメントビューア・動画ライブラリ・BGM・音声読み上げ・自動化・リモート操作／監査・放送監視など、複数の主要機能群が揃った開発段階を示します。これは安定版を意味せず、実機統合試験と録画機能などの未完了項目が残るため、引き続きα版です。

## 自動更新チャンネル

Windows Setup版ではalpha.yml／beta.yml／latest.ymlを使い分けます。beta版のリリースにはalpha向け、製品版にはbeta・alpha向けの更新ファイルも用意することで昇格に対応します。安定版を開発版へ自動変更することや、バージョンのダウングレードはしません。Portable版は現時点で自動インストール非対応です。

## バージョン更新履歴

アプリのサイドバー「バージョン・更新情報」から、各GitHub Releaseのタグ、公開日時、リリースノートを読み込みます。リリース時は変更点を正確に記載してください。過去版のリリースノートが存在しない場合、そのバージョンの追加機能や修正を推測せず、GitHub上の詳細を確認できるようにします。

## α67：更新履歴の記録と自動公開

新しいバージョンを公開する際は、`CHANGELOG.md` の先頭に `## X.Y.Z-alpha.N` 形式で見出しを作り、追加・改善・変更・修正を箇条書きで記録します。GitHub Releaseの公開処理はこの版の記録を読み込み、リリース本文に掲載します。アプリにも同梱され、GitHub APIが使えない環境でも確認できます。公開未確認の版を「公開済み」として扱わないよう区別します。

## α68：登録配信者監視の改善

監視処理は最大3件の同時確認で、利用者が設定した30〜300秒の確認間隔を処理完了後に適用します。Windows通知は任意に有効化でき、初期状態はOFFです。アプリを終了したりPCがスリープ中になった場合は監視・通知を行いません。

## α69：番組作成・引用再生の安全性

番組作成は本人のログインと明示確認を必須とし、重複作成防止記録を保存します。動画時間の補完は開始時刻を推測しません。動画リクエスト自動再生は初期OFFです。

## α70：自動アンケート・引用再生の安全性

APIから得た動画時間と引用動画IDを一致照合し、再生開始時刻が確認できない場合は投票を開始しません。ニコニコ動画情報取得APIのactionTrackIdを13桁ミリ秒形式に変更しました。アプリの再起動後は以前の引用再生時刻を信用せず、誤った自動スキップを回避します。

## α71：アンケートの開始時刻と動画尺の照合

引用再生の開始時刻を保持するのは、アプリ自身で開始した同一番組・同一動画の情報に限ります。動画尺が後から取得できた場合でも、時刻が不明または期限切れならアンケートを実行しません。自動取得には60秒間隔の再試行制限を設け、手動再取得は利用者の操作に限り許可します。

## α72：引用再生連動アンケート

自動アンケートは初期OFF。ユーザーがONに設定した場合だけ、アプリ内で引用再生を開始した動画に連動します。動画ID・番組ID・開始時刻を照合して重複を避け、「停止」操作で連動設定も解除します。

## α73：自動アンケート・放送開始時のリクエスト再生修正

自動アンケートのON設定を保存時に維持し、再生直後のニコニコ側状態反映の遅延を最大3回確認します。自動リクエストは新しい番組の終了時刻で候補を判定します。ニコニコ実配信での動作確認は引き続き必要です。

## α74：放送開始自動引用とアンケートの回帰テスト

放送開始時に使用する番組ID・リクエスト候補を固定し、認証と現在の引用状態を直前に検証します。自動アンケートの開始準備を排他し、ユーザーがOFFにした後の遅延実行を抑止します。IPCブリッジの公開漏れもCIで検出します。Windows実機・実配信検証は引き続き必要です。

## α75：自動次動画とアンケートの番組照合を修正

通常の自動次動画と放送開始時の自動再生を独立させ、アンケート継続時には番組ID・動画IDを厳密に照合します。Windows実機・実アカウントでの確認は引き続き必要です。

## α76：Windows Setup版のα自動更新改善

更新チェック時にイベントが届かなくても状態を確定し、遅延した結果でダウンロード済み状態が消えないようにしました。起動後と30分間隔で確認し、更新はバックグラウンドでダウンロードします。通常終了時に自動適用し、明示した操作からのみ最新版へ再起動します。Portable版は自動適用対象外。α連番はリリース毎に更新し、既存の実機確認が必要です。

## α77：動画尺情報取得（HTTP 406）への代替経路

既存の動画情報APIにHTTP 406等が返った場合、公式ドメインのgetthumbinfoからXMLの動画IDと再生時間を検証し、1回だけ代替取得します。両方失敗した場合は推測した尺で投票せず、手動設定へ誘導します。テストとWindows実機検証を継続します。

## α78：開発状況を反映する自動バージョン更新

直近の複数機能（放送管理、コメント、監視、自動アンケート、自動更新）が統合されているため現状は0.2系のα版を継続します。不具合修正と安全性向上を重ねたα78では`0.2.1-alpha.78`を採用しました。以降はバグ修正ならパッチ、小規模機能改善ならパッチ、主要機能追加ならマイナーを原則として自動分類します。実機検証が未完了であるため1.0への自動昇格はしません。

## α79：アプリ内更新の通知・操作を全画面に追加

新しいα版がある場合、Windows Setup版ではどの画面からでも「アプリ内で更新する」を選択でき、自動ダウンロード完了後に「更新して再起動」を明示操作できます。通常終了時の更新適用は維持し、配信中は強制再起動しません。Portable版・更新メタデータの欠けたリリースはGitHub Releasesへの案内に切り替えます。実機のインストール動作検証は引き続き必要です。

## α80：次動画の自動アンケート引き継ぎと運営コメント通知

旧投票が終わる前に切替先の自動投票要求が到着しても、対象番組・動画の一致を維持して待機し、終了後に開始できるようにしました。各投票結果の取得・判定が成功した場合のみ運営コメントで得票率を通知します。ニコニコの連投制限に合わせ5秒間隔の送信キューを利用し、既存のリクエスト受付返信と衝突しないようにしています。コメント失敗時は投票判断を変更しません。製品版ではなく0.2系αを継続し、実配信検証は必要です。

## α81：更新YMLの取得失敗時の安全な再取得

GitHubの通常の更新確認でalpha.ymlが見つからない場合、公式リリースAPIで公開されたα版のタグ・alpha.yml・Setupを照合して、同じタグの公式GitHub配布URLへ固定し再試行します。既存より新しいα版がないと正しく判定できれば最新版表示へ戻します。不完全な版はインストールせず、GitHub API自体が失敗した際も無検証の配布元へは切り替えません。alpha.Nは80→81の連番です。Windows実機更新確認は未実施です。

## α82：リクエスト・ストックの再生確認後キュー自動削除

再生成功が確認されたリクエストまたはストックを待機キューから削除します。再生情報はランタイムに保持し、アンケート・自動次動画の安全判定と再生中表示に利用します。未確認の引用再生要求・プレビュー・APIエラーでは削除しません。動画ライブラリと再生履歴は維持します。バグ修正・小規模改善によりパッチ0.2.5、連番alpha.82です。

## α83：再投票までの秒数とリクエストなしの運営コメント通知

自動アンケートの結果に基づく待機秒数を、次の投票が可能であることを確認したあと運営コメントで通知します。未再生リクエストが0件ならアンケートを省略し、運営コメントで案内します。ストックの有無ではなくリクエストの未再生件数で判定します。運営コメントは既存の通知スイッチと5秒間隔の送信キューを利用します。コード変更は小規模な機能改善としてパッチを0.2.6、alpha連番を83へ更新します。
## α84：GitHub更新404の復旧と誤った最新版判定の防止

α81のUPDATE_METADATA_NOT_FOUND対策に続き、α83で確認されたUPDATE_RELEASE_NOT_FOUNDを修正します。α版ではGitHub公式リリースAPIでtag/alpha.yml/Setupを確認してから該当リリースのURLを使うことを優先します。YML取得時・Setupダウンロード中の404では別経路を再試行し、両方失敗時にはエラーを明示します。GitHub上に新しいα版があると確認できた場合、古いフィードの応答で「最新版」としません。実Windows環境での自動アップデート試験はまだ必要です。既に動かない旧版からの移行はα84 Setupの手動インストールが必要な場合があります。
## α85：アンケートのリクエスト待機・受付時の自動再開

リクエスト0件による自動アンケート省略後、同じ番組・動画のリクエスト待機キーを保持します。正常なリクエスト受付（視聴者コメント・手動登録）をトリガーとして、未消化の受付が存在し、永続的なautoOnQuoteがONなら重複防止キーを再度利用可能にして投票開始を予約します。前の投票後処理が続いている場合は終了を待ちます。動画の残り尺・番組ID・動画ID・開始時刻を検証し、手動OFFでは起動しません。小規模修正のためパッチを0.2.8、alpha.Nを連番85に更新。実配信検証は必要です。

## α86：引用再生経過時間と次枠チェックポイント

NicoLive Helper Standaloneの表示・セッション保持方法を参考に、ニコ生の引用再生時間をプレイヤーに表示し、完走前の動画IDと経過時間を次枠のためにローカル記録します。次枠へ移る場合、途中から再生できると誤案内せず、引用APIに安全な途中シーク引数が確認できるまで、0秒からの無断再生を保留します。時刻の推定値と実際のAPI再生位置は別物です。小規模な進捗表示・記録改善としてパッチ0.2.9、alpha.86へ連番更新します。正式な引用シーク再生実装はAPI検証後の別段階です。

## α87：放送管理の操作パネル・更新表示の見やすさ改善

放送・枠管理で自動アンケートの実行状態、ニコ生の確認済み引用再生に基づく推定時計、動画リクエストとライブラリの操作をまとめて表示します。保存済み動画をキューへ追加しても自動で引用再生せず、明示操作による確認を必須にします。自動更新欄を全画面で常時表示し、バージョン・更新情報を読みやすいカードへ整理しました。小規模な画面・操作改善としてパッチ番号を0.2.10、α連番を87へ進めます。Windows実機での操作とニコ生実配信の最終確認は引き続き必要です。

## α88：放送・枠管理のReferenceErrorを修正

α87で追加した配信中の操作パネルで、定義されていない`libraryLoading`と`libraryError`を参照し、メニューの「放送・枠管理」を開くと`ReferenceError`になる問題を修正しました。実際に定義された`videoLibraryLoading`と`videoLibraryError`を使い、ライブラリの取得中・取得失敗の状態を正しく表示します。レンダラー内のモデル生成処理を実行する回帰テストを追加しました。小規模な不具合修正のため0.2.11、連番alpha.88へ更新します。Windows実機の操作とニコ生実配信の検証は別途必要です。

## α89：放送監視・番組作成／終了の独立ページと自動無料延長

「24時間放送監視」と「番組枠の作成・終了」を「放送・枠管理」から独立したページへ分離。従来の操作・保存設定を引き継ぎます。自動延長は従来設定UIと延長可能方法の取得だけで実行されていなかったため、Electronメインプロセスにアプリ起動中の監視処理を実装。自分の放送履歴・現在のON_AIR状態・実際の終了時刻・延長方法が全て確認でき、終了5分前に無料の選択肢が存在する場合のみ延長要求を送信します。有料・ポイント・チケット消費は行わず、同じ終了予定時刻への自動重複送信を防ぎます。延長後の終了時刻を再照合し、不明な場合は公式画面で確認を求めます。大きな機能追加のためベース番号を0.3.0、alpha.Nを89へ更新。古い非公開延長APIに依存し、実配信での成功検証は未実施です。アプリ終了・PCスリープ中は監視できません。

## α90：自動更新HTTP 404の公式配布ファイル検証付き代替経路

GitHubの最新公開α版にalpha.ymlとSetup版があるのにelectron-updaterの確認・ダウンロードでHTTP 404になる場合、固定された公式GitHub Releases APIから照合済みのSetupアセット名・アセットID・SHA256を取得します。通常のGitHubと固定リリース両経路が404の場合にのみ、リリースのブラウザ用URL、次に公式APIアセットURLでWindows Setupを取得します。ストリーミング保存・ファイルサイズ上限・SHA256照合を必須とし、一致しなければファイルを削除し起動しません。既存のelectron-updaterが成功すれば従来どおりアプリ終了時に自動適用、代替経路では明示操作でSetup版を起動してインストールします。Portable版は従来どおり自動適用非対応。ネットワーク上の404の根本原因は実機環境のログがないため確定しておらず、Windows実機の新経路は引き続き検証が必要です。小規模修正のため0.3.1-alpha.90を使用します。
